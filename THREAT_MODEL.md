# KeyFort Threat Model

## 1. System Overview and Security Objectives

KeyFort is a credential vault and ephemeral guest pass broker. Passwords are encrypted client-side, and ephemeral guest passes allow single-use login without exposing master or site passwords.

KeyFort does not claim full zero-knowledge confidentiality across all attributes: the server can see site names and account usernames, but never plaintext passwords or vault encryption keys.

The primary objectives are:
1. Protect permanent passwords from unauthorized access, sync server compromise, and unauthorized device sync.
2. Enable owners to grant single-use, temporary access to a cooperating target site without disclosing the owner's master password or permanent credentials.
3. Eliminate credential replay risks by invalidating guest access immediately after first use and triggering vault key rotation.

## 2. Assets

- **Master Secret**: Plaintext master password held exclusively by the user and never transmitted over the network.
- **Key Encryption Key (KEK)**: Derived client-side from the master secret using PBKDF2 with HMAC-SHA256 (600,000 iterations).
- **Data Encryption Key (DEK)**: Random 256-bit symmetric key that wraps per-entry keys. Stored encrypted under KEK via AES-256-GCM.
- **Vault Entries**:
  - Site domain/name.
  - Account username.
  - Account password (AES-256-GCM ciphertext bound to entry ID and key version).
- **Guest Pass Tokens**: High-entropy 128-bit ephemeral tokens broker access to a designated account.
- **Target Site Temporary Credentials**: Short-lived credentials generated by a cooperating site for a guest pass session.
- **Audit Ledger**: Append-only sequence of hash-chained blocks recording security events and key rotations.

## 3. Attacker Profiles and Threat Vectors

1. **Compromised or Untrusted Server Operator**:
   - Attacker has administrative access to the KeyFort server, database, and transit logs.
   - Capability: Inspect all stored records, tamper with ciphertext, inject fraudulent ledger entries, or forge access responses.
2. **Untrusted Guest Recipient**:
   - Recipient of a guest pass who may attempt to extract permanent credentials, reuse temporary tokens, or extend session lifespan beyond authorization.
3. **Physical / Shoulder-Surfing Observer**:
   - Observer or camera capturing screen contents during token generation or redemption.
4. **Network Adversary (Passive / Active MITM)**:
   - Adversary intercepting network communications between client devices, the KeyFort server, and target sites.
5. **Stolen or Compromised Secondary Device**:
   - Previously trusted device that is stolen, compromised, or operating outside normal behavioral parameters.

## 4. Current Implementation State and Server Visibility

- **Plaintext Metadata Visibility**: In `org.keyfort.core.Entry`, JPA `EntryEntity`, and `EntryDto`, `site` and `username` fields remain plaintext. The `site` name stays readable because the server uses it to select the target `SiteConnector` SPI during pass creation and webhook routing. `username` encryption inside the sealed payload is deferred as future work to preserve client listing performance without decrypting all entries. The server can see site names and usernames, but never plaintext passwords or the DEK. (Architectural decision recorded in ADR 0011).
- **JWT Key Fail-Fast**: Implemented in Phase 6. The server validates `KEYFORT_JWT_SECRET` on startup and aborts if missing or under 32 bytes (256 bits). Default fallback is strictly confined to `dev` and `test` profiles.
- **Access Restrictions**: Protected endpoints require JWT authentication with explicit CORS allow-listing restricting authorized origins, headers, and HTTP methods.

## 5. Security Guarantees (Phases 2-5 Target Design)

- **Separation of Concerns**: Guest credentials are generated by target site connectors or broker mechanisms. A guest pass never exposes the vault DEK or the owner's permanent password.
- **Hashed Token Storage**: The server stores only the SHA-256 hash of ephemeral guest tokens. Constant-time comparisons are used to prevent timing attacks.
- **Strict Single-Use State Machine**: Ephemeral tokens advance through `CREATED -> ISSUED -> REDEEMED -> CONSUMED -> BURNED`. Concurrent redemption requests are resolved atomically such that exactly one caller succeeds.
- **Post-Login Invalidation and Rotation**: Upon receipt of a verified login webhook from a cooperating site, the guest pass credential is revoked on the target site, marked burned, and vault key rotation is requested.
- **Zero-Knowledge Key Rotation Delegation**: The server never holds the user's master key, KEK, or decrypted vault DEK. Consequently, upon burning a guest pass, the server cannot re-encrypt vault entries itself. The server flags `rotationPending = true` on the vault record. Key rotation is executed client-side by the owner's authenticated client at next unlock.
- **Guest Session Control & Isolation**: Target sites integrated via the connector SPI enforce a dual session timeout (hard TTL default 10 minutes, idle timeout default 5 minutes) and validate every protected request against the database repository (`GuestSessionRepository`). The pass reaching `BURNED` initiates key rotation but does NOT terminate the friend's active browser session, ensuring normal guest usage without premature disruption. An authenticated owner kill-switch (`POST /api/guest-passes/{id}/end-session`) enables immediate remote session termination via HMAC-authenticated connector calls.
- **Best-Effort Device Binding**: Target site guest sessions are optionally bound to the SHA-256 hash of `User-Agent` + random device cookie (`KEYFORT_DEVICE_ID`). This provides defense-in-depth against simple session cookie exfiltration across devices or browsers. However, as documented in non-goals, an attacker with full local system access or identical User-Agent replay can mimic this binding.
- **Tamper Evidence**: Cryptographic operations verify Authenticated Additional Data (AAD) bound to entry IDs and key versions. Tampered ciphertext or ledger records fail verification deterministically.

## 6. Explicit Non-Goals and Limitations

KeyFort explicitly does not protect against the following threat scenarios:

1. **Live Session Interception on Target Sites**:
   - Once a guest redeems a credential and establishes an active HTTP session on a cooperating site, KeyFort provides session tracking and a remote kill-switch via the connector SPI (`DELETE /connector/sessions/{id}`). However, on sites without connector integration (Assisted mode), remote session termination is impossible. Device binding (User-Agent + device cookie) is strictly best-effort defense-in-depth and cannot withstand full endpoint compromise or device replication.
2. **Camera Recording During Active Display**:
   - If an owner or guest displays a credential or token on screen in direct view of a recording camera, the optical capture of that displayed secret cannot be prevented by software. KeyFort limits the window of exposure by enforcing single-use destruction and short timeouts, making the recorded value obsolete after initial redemption.
3. **Compromised Client Endpoints**:
   - If the host operating system or device running KeyFort contains malware, keyloggers, or memory dumpers, client memory can be read while the vault is in an unlocked state. Zero-knowledge protections apply only while at rest or against server compromise.
4. **Sites Without Connector Integration**:
   - On sites that do not implement the KeyFort connector SPI, KeyFort cannot broker temporary credentials or receive automated login webhooks. For these sites, KeyFort offers only an assisted workflow reminding the owner to update the permanent password after sharing.
